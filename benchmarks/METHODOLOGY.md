# Benchmark Methodology

## What we measure

### Primary metrics

1. **Main pass ops/sec** — permission operations (setxattr or chmod) per second during the main pass only. This isolates the apply throughput from enumeration and pre-pass overhead.

2. **Overall ops/sec** — total objects processed divided by total wall-clock time, including pre-pass and enumeration. This is the number that determines how long a real run takes.

3. **Pre-pass time** — wall-clock time for the top-down directory permission fix. Measured separately because it's a fixed cost that scales with directory count, not file count.

4. **Validate rate** — getxattr + byte-compare operations per second. Read-only, no writes. Measures how fast we can verify a completed run.

### Secondary metrics

- **Peak RSS** — maximum resident set size. Important because the tool must run on constrained clients alongside other workloads.
- **Error count** — must be 0 for a valid benchmark run. Any errors invalidate the measurement.
- **Skip count** — for `--compare` runs, confirms that comparison logic works and that the previous apply was complete.

## Why these metrics

**Main pass ops/sec** is the core throughput number. It tells us how fast the setxattr syscall path is, independent of enumeration strategy. This is the number to optimize.

**Overall ops/sec** matters for capacity planning. A customer asking "how long will this take on my 500M-object filesystem" needs the overall rate, not the main-pass rate.

**Pre-pass time** is tracked separately because it has different scaling characteristics. It scales with directory count and is bound by NFS readdir round-trips, not CPU or setxattr throughput. Optimizing it requires reducing round-trips (e.g., batching, caching), not adding workers.

**Validate rate** matters because production workflows run validate after apply to confirm correctness. If validate is slower than apply, it becomes the bottleneck in the overall workflow.

## How we measure

### Dataset generation

Test datasets are generated by three tools:

- `generate-tree` (Go, Linux/NFS) — named-principal NFSv4 ACLs via direct setxattr. 15 scenarios (deny, non-canonical order, inherit-only, no-propagate, append-only, protected DACL, etc.). Group principals carry the NFSv4 `g` flag. Safety ACE auto-detected. Fastest option: 1M files with ACLs in ~3.4 min.
- `generate_tree.py` (Python, Linux) — POSIX mode scrambling via RFT (pchmod). No ACLs. Uses `--copies`/`--seed-files`/`--jobs` for scale.
- `generate_tree_windows.py` (Python, Windows/SMB) — SDDL security descriptors via Set-Acl with domain SIDs. 15 scenarios matching the Go generator. Slow (~12-22 paths/sec over SMB).

| Scale | Approximate objects | Directories | Generator |
|---|---|---|---|
| small | 500 | ~100 | all three |
| medium | 5,000 | ~1,000 | all three |
| large | 40,000 | ~6,000 | all three |
| xlarge | 1,000,000+ | ~100,000+ | generate-tree (Go), generate_tree.py |

For named-principal ACL testing, prefer `generate-tree` (Go). It produces trees with the same scenario coverage as the Windows generator but 200x faster at large scale.

Windows-generated trees (`generate_tree_windows.py`) produce files with domain-owner SIDs and scrambled Windows ACLs (icacls recipes: inheritance disabled, contradictory deny/grant, lockout, read-only). This is the realistic starting state for eDiscovery data.

### Pre-run state

Before each benchmark run, the tree must be in a "bad" state so the pre-pass and apply have real work to do. A repeat run on an already-correct tree measures skip throughput, not apply throughput.

Re-scramble for bigdata:
```bash
pchmod -R 0777 /mnt/fb-perms/bigdata
for d in hr marketing legal; do pchmod -R 0644 /mnt/fb-perms/bigdata/$d; done
for d in infra ops; do pchmod -R 0700 /mnt/fb-perms/bigdata/$d; done
```

Mode 0644 on directories is the useful case: it blocks traversal, so the pre-pass must recover subtrees before enumeration can reach them.

For Windows-generated trees, the scrambled state is the default after generation.

### Run protocol

1. **Re-scramble** the tree (or use a freshly generated one).
2. **Apply** with the target spec: `./permissionreset -spec <spec> <target>`
3. **Record** the output (ops/sec, elapsed, errors, pre-pass time).
4. **Validate** immediately after: `./permissionreset -spec <spec> -validate <target>`
5. **Compare run** to confirm skipping: `./permissionreset -spec <spec> -compare <target>`

All three steps must show 0 errors for a valid benchmark.

### What we do NOT measure in benchmarks

- **Dry-run throughput** — not representative of real I/O; useful for testing but not for performance characterization.
- **pfind enumeration** — the built-in parallel walk is the default and faster (readdir reports entry type for free; pfind emits bare paths requiring lstat).
- **SMB backend** — not the target use case; known path-mapping issue (RISKS.md #8).
- **Network or storage-side metrics** — we measure client-side throughput only. FlashBlade-side metrics (IOPS, latency distribution) are out of scope for this tool's benchmarks.

### Controlling for NFS caching

NFS attribute caching can inflate apparent throughput on repeat runs. The mount uses `noatime,nodiratime` to reduce but not eliminate caching effects. The re-scramble step ensures the attribute cache is populated with stale data, so the apply path does real work.

The `--compare` flag adds a getxattr before each write. On a first run (all mismatched), this adds ~20% overhead. On a repeat run (all matching), it measures pure getxattr + compare throughput.

### Reproducing results

All benchmarks are run on the same client and mount. Results will vary on different hardware, NFS server firmware versions, network topology, and mount options. The key mount options that affect throughput:

- `nconnect=16` — multiple TCP connections to the NFS server; critical for parallelism.
- `vers=4.1` — NFSv4.1 required for session trunking with nconnect.
- `noatime,nodiratime` — reduces metadata updates on read.

Dropping `nconnect` from 16 to 1 typically reduces throughput by 4-8x on metadata-heavy workloads.
