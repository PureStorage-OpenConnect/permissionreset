What this file does

When you right-click a folder in Windows and open the Security tab, you see a list of users and groups, each with Allow/Deny checkboxes for permissions like "Read," "Write," "Full Control." A permissionreset spec file is the text equivalent of that dialog—it describes what the permissions should look like, and permissionreset stamps them onto every file and folder in a directory tree.

The spec is a YAML file. You pass it with --spec:

permissionreset --spec myspec.yaml /mnt/data/share

permissionreset reads the spec, walks every file and directory under /mnt/data/share, and sets permissions to match.

The skeleton

Every spec file has this shape:

protocol: nfsv4          # or "posix"

default:
  acl:
    - "A::OWNER@:rwaTcCoy"
    - "A:g:GROUP@:rncy"
    - "A::EVERYONE@:rncy"

rules:
  - match:
      type: directory
    acl:
      - "A:fd:OWNER@:rwaDxtTcCoy"
      - "A:fdg:GROUP@:rxtncy"
      - "A:fd:EVERYONE@:rxtncy"

  - match:
      type: file
      pattern: "*.sh"
    acl:
      - "A::OWNER@:rwaxTcCoy"
      - "A:g:GROUP@:rxncy"

exclude:
  - ".snapshot"
  - "*.tmp"

Three sections:

SectionPurpose
protocolWhich permission system to use
default + rulesWhat permissions to set on what
excludeWhat to skip

Protocol

protocol: nfsv4

Two choices:

  • posix — Traditional Unix permissions (owner/group/other, the chmod 0755 style). Simple but limited: three permission slots, no named users or groups beyond owner and group.
  • nfsv4 — NFSv4 ACLs. The NFS equivalent of what you see in the Windows Security tab: a list of entries, each granting or denying specific permissions to a specific user or group. This is what you want for FlashBlade multiprotocol shares.

The protocol determines which fields are valid. An nfsv4 spec uses acl: lists. A posix spec uses mode:. Mixing them is an error—permissionreset rejects it before touching any files.

POSIX specs (the simple case)

If you only need basic Unix permissions, POSIX specs are straightforward:

protocol: posix

default:
  mode: "0664"
  owner: serviceaccount
  group: engineering

rules:
  - match:
      type: directory
    mode: "2775"

  - match:
      type: file
      pattern: "*.sh"
    mode: "0775"

Mode strings

Mode is a four-digit octal number in quotes. If you have used chmod, this is the same thing:

Digit positionControlsCommon values
First (special)setuid / setgid / sticky0 = none, 2 = setgid, 4 = setuid
Second (owner)Owner permissions7 = rwx, 6 = rw-, 5 = r-x
Third (group)Group permissions7 = rwx, 5 = r-x, 4 = r--
Fourth (other)Everyone else5 = r-x, 4 = r--, 0 = ---

"2775" means: setgid + owner rwx + group rwx + other r-x. Setgid on a directory makes new files inherit the directory's group—useful for shared project folders.

Owner and group

owner: serviceaccount
group: engineering

These set the file owner and group. They require --set-owner on the command line (and root or CAP_CHOWN on the system). Without --set-owner, permissionreset ignores these fields.

NFSv4 specs (the Windows-like ACLs)

This is where the real power is, and where the syntax needs explanation.

How NFSv4 ACLs map to the Windows Security tab

In Windows, the Security tab shows something like:

Group or user names:
  Administrators        Allow: Full Control
  DOMAIN\ProjectTeam    Allow: Read & Execute
  DOMAIN\Auditors       Allow: Read
  Everyone              Deny: Write

Each row is an Access Control Entry (ACE). The full list is the Access Control List (ACL). NFSv4 ACLs work the same way—an ordered list of entries, each granting or denying permissions to someone.

The difference is the syntax. In Windows you click checkboxes; in an NFSv4 spec you write a compact string.

Reading an ACE string

Every ACE is a colon-separated string with four fields:

A:fdg:storageadmins@example.com:rwaDxtTcCoy
│  │    │                          │
│  │    │                          └─ Permissions (what they can do)
│  │    └─ Who (which user or group)
│  └─ Flags (inheritance + group marker)
└─ Type (Allow or Deny)

Field 1: Type — Allow or Deny

LetterMeaningWindows equivalent
AAllowA checkmark in the Allow column
DDenyA checkmark in the Deny column
UAudit"Auditing" entries in Advanced Security Settings — goes in sacl:, not acl: (see below)
LAlarmNot accepted

You will almost always use A (Allow). Deny rules (D) go before Allow rules—order matters, just like in Windows Advanced Security Settings.

Field 2: Flags — Inheritance

In Windows, when you open Advanced Security Settings and look at the "Applies to" column, you see values like "This folder, subfolders and files" or "This folder only." Flags are the NFSv4 way of expressing the same thing.

FlagNameWhat it means
fFile inheritNew files in this directory inherit this ACE
dDirectory inheritNew subdirectories inherit this ACE
gGroupThis ACE applies to a group, not a user
iInherit-onlyThis ACE applies only to children, not to the directory itself
nNo-propagateChildren inherit this ACE but don't pass it to their children

The flags you will use most:

FlagsWindows "Applies to" equivalent
(empty)This object only
fdThis folder, subfolders and files
dThis folder and subfolders
fThis folder and files
fdiSubfolders and files only (not this folder)
g(marks the principal as a group—see below)
Important

The g flag is special. It does not control inheritance. It tells the system that the principal is a group, not a user. The NFS kernel needs this to look up the name correctly. Every group principal must have g in its flags. Forgetting g on a group is a common mistake that causes silent lookup failures.

For directories, you almost always want fd (file and directory inherit) so permissions flow down to new files and subdirectories. For files, you use no inheritance flags (files cannot have children).

This is why most specs have separate rules for directories and files:

rules:
  # Directories get inheritable ACEs
  - match:
      type: directory
    acl:
      - "A:fd:OWNER@:rwaDxtTcCoy"       # fd = inherit to files and dirs
      - "A:fdg:GROUP@:rxtncy"            # fdg = inherit + it's a group

  # Files get non-inheritable ACEs
  - match:
      type: file
    acl:
      - "A::OWNER@:rwaTcCoy"             # no flags = this object only
      - "A:g:GROUP@:rncy"                # g only = group, no inherit

Field 3: Who — The principal

This is the user or group the ACE applies to. Three formats:

Special principals

Work everywhere, no configuration needed:

PrincipalWindows equivalent
OWNER@The file's owner (like "CREATOR OWNER")
GROUP@The file's primary group (like "CREATOR GROUP")
EVERYONE@Everyone (like the "Everyone" group)

Named principals

Require idmapd/SSSD configured for the domain:

arraysvc@corp.example.com
storageadmins@corp.example.com

These are like DOMAIN\username in Windows but written as name@domain. They require the NFS client's identity-mapping service (idmapd) to resolve the name. If idmapd is not configured for the domain, setxattr fails with EINVAL.

Numeric IDs

Always accepted, but may not round-trip cleanly:

10001
1000001138

These are raw UID/GID numbers. The kernel may resolve a numeric ID to user@domain before sending it to the server. If that happens, the stored form differs from what you wrote, and --compare and --validate report mismatches.

Recommendation

After a test apply, run nfs4_getfacl on one object and use whatever form the server actually stored. That is the only way --compare and --validate produce correct results.

Compare to the Windows "basic permissions":

There is no single "Full Control" shorthand. You spell out every letter. This is intentional—it forces you to be explicit about what you are granting.

The rules engine

How matching works

permissionreset walks every file and directory. For each one, it checks the rules in order, top to bottom, and uses the first match. If nothing matches, it uses default.

This is exactly like Windows' inherited vs. explicit ACLs—more specific rules go first, catch-all at the bottom.

default:
  acl: [...]        # catch-all: anything not matched by a rule

rules:
  - match:
      type: directory   # matches all directories
    acl: [...]

  - match:
      type: file
      pattern: "*.sh"   # matches only .sh files
    acl: [...]

  - match:
      type: file        # matches all remaining files
    acl: [...]

Match criteria

Each rule has a match: block with two optional fields:

FieldValuesBehavior
typefile, directory, or omitRestricts to files or directories. Omit to match both.
patternA glob like *.shMatched against the base name only (not the full path). * matches any sequence except /, ? matches one character, [abc] matches a character class.

If both are omitted, the rule matches everything—put it last or it will shadow all rules after it.

Rules replace, they do not merge

Critical

A matching rule replaces the default entirely. It does not inherit anything from default.

In Windows terms: imagine the Security tab where a subfolder has "Include inheritable permissions from this object's parent" unchecked. The subfolder's ACL is entirely its own.

Example of the trap:

protocol: posix
default:
  mode: "0664"
  owner: serviceaccount
  group: engineering

rules:
  - match:
      type: file
      pattern: "*.sh"
    mode: "0775"
    # owner and group are NOT inherited from default!
    # This rule sets mode only. Owner/group are left alone.

For *.sh files, the effective permissions are mode: "0775" and nothing else. If you want scripts to also get owner: serviceaccount and group: engineering, you must say so in the rule:

  - match:
      type: file
      pattern: "*.sh"
    mode: "0775"
    owner: serviceaccount
    group: engineering

Rule ordering strategy

  1. Directory rules — with inheritance flags (fd)
  2. Specific file rules — pattern matches (*.sh, *.dat)
  3. General file rule — catches remaining files
  4. Default — catches anything not matched above

Exclude patterns

Skip files or directories that should not be touched:

exclude:
  - ".snapshot"
  - "*.tmp"
  - "logs/*.gz"

You can also add excludes on the command line with --exclude. Both sources are merged (neither overrides the other).

PatternBehavior
No / in patternMatched against the base name at any depth. .snapshot matches every .snapshot directory anywhere in the tree.
Contains /Matched against the path relative to the target root. logs/*.gz matches .gz files in the logs/ directory directly under the target, but not in data/logs/.

Excluded directories are pruned—permissionreset does not descend into them, saving traversal time. This is the right way to skip .snapshot directories on FlashBlade (they can contain millions of objects).

Restrictions:

  • No ** (Go's glob has no recursive wildcard)
  • No absolute paths (patterns are always relative to the target root)

Worked example

Scenario: a shared project directory on FlashBlade accessed over NFS. Three groups need access:

  • storageadmins — full control (they manage the share)
  • engineering — read, write, execute
  • auditors — read only

The NFS user running permissionreset is arraysvc.

protocol: nfsv4

# Files that don't match any rule get this ACL.
# In practice, the file rule below catches all files,
# so this is a safety net.
default:
  acl:
    - "A::arraysvc@example.com:rwaDdxtTnNcCoy"
    - "A:g:storageadmins@example.com:rwaDdxtTnNcCoy"
    - "A:g:engineering@example.com:rwadxtTnNcy"
    - "A:g:auditors@example.com:rxtncy"

rules:
  # Directories: same principals, but with inheritance flags
  # so new files/subdirs pick up these ACEs automatically.
  - match:
      type: directory
    acl:
      - "A:fd:arraysvc@example.com:rwaDdxtTnNcCoy"
      - "A:fdg:storageadmins@example.com:rwaDdxtTnNcCoy"
      - "A:fdg:engineering@example.com:rwadxtTnNcy"
      - "A:fdg:auditors@example.com:rxtncy"

  # Shell scripts: engineering gets execute
  - match:
      type: file
      pattern: "*.sh"
    acl:
      - "A::arraysvc@example.com:rwaDdxtTnNcCoy"
      - "A:g:storageadmins@example.com:rwaDdxtTnNcCoy"
      - "A:g:engineering@example.com:rwaxdtTnNcy"
      - "A:g:auditors@example.com:rxtncy"

  # All other files: engineering can read and write but not execute
  - match:
      type: file
    acl:
      - "A::arraysvc@example.com:rwaDdxtTnNcCoy"
      - "A:g:storageadmins@example.com:rwaDdxtTnNcCoy"
      - "A:g:engineering@example.com:rwadtTnNcy"
      - "A:g:auditors@example.com:rtncy"

exclude:
  - ".snapshot"

What happens for each object type:

ObjectMatched byACL applied
/mnt/data/share/directory rule4 ACEs with fd/fdg flags
/mnt/data/share/src/directory ruleSame 4 inheritable ACEs
/mnt/data/share/deploy.sh*.sh file rule4 ACEs, engineering gets x
/mnt/data/share/README.mdgeneric file rule4 ACEs, engineering has no x
/mnt/data/share/.snapshot/excludedSkipped entirely (not descended)

Why arraysvc is listed first

The user running permissionreset needs traverse permission (x on directories, read on the ACL) throughout the tree. If permissionreset fixes a directory's ACL and the new ACL locks out the running user, it cannot descend into that directory to fix its children. Putting the running user first with full control prevents this.

Common mistakes

Forgetting g on group principals

Wrong
"A:fd:storageadmins@example.com:rwaDxtTcCoy"
Right
"A:fdg:storageadmins@example.com:rwaDxtTcCoy"

Without g, the NFS kernel tries to look up storageadmins as a user, which either fails or maps to the wrong entity.

Using inheritance flags on file rules

Wrong
"A:fd:OWNER@:rwaTcCoy"
# files cannot have children
Right
"A::OWNER@:rwaTcCoy"
# no inheritance flags on files

Mixing protocol fields

# WRONG: mode is a posix field, acl is an nfsv4 field
protocol: nfsv4
default:
  mode: "0755"
  acl:
    - "A::OWNER@:rwaDxtTcCoy"

permissionreset rejects this at load time. Pick one protocol.

Relying on OWNER@ in production

OWNER@ resolves to whoever owns the file right now. On Windows-written data imported to FlashBlade, that might be nobody or a numeric ID without traverse permission. Use named principals in production specs; reserve OWNER@ / GROUP@ / EVERYONE@ for quick tests.

Assuming the default inherits into rules

default:
  acl:
    - "A::arraysvc@example.com:rwaDdxtTnNcCoy"
    - "A:g:storageadmins@example.com:rwaDdxtTnNcCoy"
    - "A:g:auditors@example.com:rxtncy"

rules:
  - match:
      type: directory
    acl:
      - "A:fd:OWNER@:rwaDxtTcCoy"
      # arraysvc, storageadmins, auditors are NOT here.
      # Directories get ONLY the one OWNER@ ACE.

Audit ACEs (SACL) on FlashArray

A FlashArray NFSv4 ACL holds two lists in one attribute: the DACL (A allow and D deny entries, who may do what) and the SACL (U audit entries, which accesses get logged). permissionreset writes the SACL from a separate sacl: key. U and L lines are refused in acl:.

Both FlashArray and FlashBlade (multiprotocol file systems, Purity//FB 4.8.0 measured) return audit ACEs inside system.nfs4_acl, so on both a DACL write without them deletes them (RISKS.md #10, #51). The section was written against FlashArray; FlashBlade SACL writes over NFS are stored but otherwise untested. All of it needs --sacl. Without --sacl, a DACL reset is refused when the target root already carries audit ACEs.

Writing an audit ACE

An audit ACE uses the same four fields as any other ACE, with type U and one or both of two extra flags:

FlagNameWhat it means
SSuccessful accessLog accesses that were allowed
FFailed accessLog accesses that were denied

A U ACE must carry S, F or both. The permission letters say which accesses to log. The inheritance flags work as they do for A/D: directories carry fd so new children inherit the audit entry, and files carry none.

sacl:
  - "U:fdSF:EVERYONE@:rwadxTNcCoy"   # directory: log every allowed and denied access, inherited

Only U is accepted in sacl:. L (alarm) ACEs cannot be written, and FlashArray does not act on them.

Two kinds of rule

Rule hasWhat permissionreset writes on each object it matches
sacl: and no acl:Keeps the object's own DACL and replaces only its SACL.
acl: and sacl:The spec's DACL and the spec's SACL, as given. The object's DACL is replaced.

The first kind is the one to use on a migrated tree whose DACLs differ from object to object. For each object, permissionreset reads the ACL, keeps every A/D entry byte for byte in its original order, drops every U/L entry, adds the rule's SACL at the end, and writes the result. The result depends only on the object's DACL and the spec, so a second run changes nothing (with --compare, a rerun writes 0 objects).

examples/nfsv4_sacl_keep_dacl.yaml is a complete DACL-keeping spec:

protocol: nfsv4
rules:
  - match: {type: directory}
    sacl:
      - "U:fdSF:EVERYONE@:rwadxTNcCoy"
  - match: {type: file}
    sacl:
      - "U:SF:EVERYONE@:rwadxTNcCoy"

An object whose ACL has no A/D entries is not written and is reported as failed: a SACL-only ACL would take away all access.

sacl: [] means "no audit ACEs". On a DACL-keeping rule it removes every audit ACE and keeps the DACL. On a rule with acl: it writes the DACL with an empty SACL.

--validate on a DACL-keeping rule checks only the SACL: the object's U entries must match the spec's, in order, at the end of the ACL. The DACL is not compared, because the spec does not define one.

SACL mode: --sacl

Writing audit ACEs is opt-in. Without --sacl, permissionreset runs acl: specs as it always has, and refuses any spec that names sacl: (sacl: [] included, since it deletes audit ACEs):

ERROR: the following NFSv4 rule(s) set sacl: (audit ACEs):
  rule[0]
Writing audit ACEs is SACL mode. Pass --sacl to turn it on.

With --sacl, a second check applies. On FlashArray, writing a DACL with no SACL deletes the object's existing audit ACEs, so an NFSv4 rule (or default:) that sets acl: and has no sacl: key at all is refused before anything is touched:

ERROR: the following NFSv4 rule(s) set acl: with no sacl: key:
  rule[0]
On FlashArray, writing the DACL without a SACL deletes the object's existing audit ACEs.
Add sacl: [] to that rule to say an empty audit ACL is intended, or run without --sacl if this is not a FlashArray SACL run.

--sacl also turns on the preflight and the audit-policy NOTE.

Important

Without --sacl, only the root is checked. An acl: spec without --sacl is refused when the target root carries audit ACEs, and under --compare so is each object that carries them. A subtree with audit ACEs under a root without them is not caught unless --compare is on, and that run deletes them, on FlashArray and FlashBlade alike (RISKS.md #10). On any tree that uses auditing, always pass --sacl.

Required privilege: the audit bypass

Writing audit ACEs needs the array's audit bypass. That means one of:

  • root over AUTH_SYS with root squash off on the export (kernel transport: mount NFSv4.1 as root; userspace transport: --auth-uid 0), or
  • an AD identity the array grants the bypass directly.

Domain Admins membership is not enough.

The bypass covers the read too. On Purity//FA before 6.12.1, an ACL read by an identity without the bypass empties the SACL of an object that is still inheriting it. So the bypass is required, not optional, and there is no flag to skip the check.

The preflight

Any --sacl run of a spec with a sacl: key — sacl: [] included, since that rule still reads every object — runs a probe in apply, --compare and --validate alike, but not in --dry-run. The probe runs before the walk: it writes a temporary file with a DACL and an audit ACE, then reads it back.

  • If the write is refused, the run stops with preflight: audit (SACL) ACE write was refused -- the running identity lacks the array's audit bypass, followed by the list of identities that have the bypass.
  • If the write is accepted but the read-back has no U entries, the run stops with preflight: audit (SACL) ACEs were accepted but the array did not retain them.

Every such run also prints this NOTE, whatever the preflight finds:

NOTE: sacl: writes audit ACEs, but logging them still needs an audit policy turned
      on for the managed directory -- permissionreset cannot check that over NFS.

Limits

  1. New objects are not protected on Purity//FA 6.10.6 and 6.11.x. Files and folders created after the run inherit from their parent, and one ACL read over NFSv4.1 by a user without the bypass leaves them with an empty SACL. SMB reads do not do this. 6.12.1 fixed it. Use 6.12.1 or later where auditing must hold, or rerun permissionreset on a schedule.
  2. Parent SACL edits do not reach stamped children. Every object holds its own copy. To change the audit rule, change the spec and rerun.
  3. Logging needs an audit policy on the managed directory. The SACL is stored without one, but nothing is logged. permissionreset cannot check this over NFS.
  4. 64 KB ACL size. XATTR_SIZE_MAX bounds the encoded ACL. A very large DACL plus SACL fails that object with E2BIG.
  5. The read-write gap (DACL-keeping rules). A DACL change someone makes between permissionreset' read and its write of the same object is lost. The window is milliseconds per object. Run in a quiet window.
  6. Replacing a file avoids its SACL. In place, a user without the bypass cannot remove the SACL (not by a DACL write, chmod or nfs4_setfacl -x) on 6.10.6 or 6.12.1. A file that is copied and renamed over the original, or re-created, carries only the parent's inherited SACL, so on 6.10.6/6.11.x it is exposed to limit 1.

Capturing a SACL spec with build-spec

build-spec reads one directory and one file and decides by what it finds:

  • No audit ACEs: the same DACL spec as before, with no sacl: key. It runs without --sacl. To run it in SACL mode, add sacl: [] (or the audit ACEs you want) to each rule.
  • Audit ACEs: DACL-keeping sacl:-only rules, run with --sacl. An exemplar with none of its own gets sacl: []. --with-dacl adds the exemplars' DACLs as acl: as well, which turns the rules into ones that replace every object's DACL.

L ACEs are dropped with a NOTE. Capture FlashArray exemplars with the bypass: without it the array returns no audit ACEs, and before 6.12.1 that read also empties an inheriting SACL on the exemplar.

Validating your spec

Before running a real repair:

# Dry run: shows what would happen, changes nothing
permissionreset --spec myspec.yaml --dry-run /mnt/data/share

# Apply to a small test directory first
permissionreset --spec myspec.yaml /mnt/data/share/testdir

# Verify after applying: checks every object matches the spec
permissionreset --spec myspec.yaml --validate /mnt/data/share/testdir

For a spec with sacl:, add --sacl to each command (see SACL mode).

Spec validation happens at load time. If you have a typo in a permission letter, an invalid glob pattern, or a cross-protocol field, permissionreset tells you immediately and exits before touching anything.
